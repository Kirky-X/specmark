# Clarify — propose 前的结构化澄清

`propose` 的可选前置步骤。当用户描述包含歧义、否则会迫使提案猜测时触发。Clarify 问少量高影响问题，把每个答案写入 `proposal.md` 的 `## Clarifications` 节，然后交给 `propose`。

**定位**：可选，在 `propose` 之前。请求已具体时跳过。绝不替代 `explore`（开放式思考）—— clarify 是对 8 个分类的有界问答。

**输入**：用户对想做的变更的描述。可显式调用 `/specmark clarify <name>`，或由 `propose` 检测到歧义时建议触发。

**Steps**

0. **先探上下文再提问**

   在向用户提问前，用工具快速调研项目现状：

   - Glob 相关代码目录，了解现有结构和模式
   - 检查最近 git 变更（`git log --oneline -5`），了解项目方向
   - 读相关文档/配置，识别已有约束

   **目的**：形成初步理解后，问出的问题才有的放矢，避免问用户"你的代码在哪"这种低价值问题。

1. **跨 8 个分类扫描描述**

   把用户描述对到 8 类覆盖扫描上。对每个分类判断：*已覆盖* / *有歧义* / *缺失*。只有标记为 *有歧义* 或 *缺失* 的分类才可能产出问题。

   | 分类              | 问什么                                                       |
   | ----------------- | ------------------------------------------------------------ |
   | Functional Scope  | 什么在/出范围；显式 non-goals                                |
   | Domain            | 领域特定规则、实体、不变量                                   |
   | UX                | 用户侧流程、错误状态、反馈                                   |
   | NFR               | 性能、可用性、耐久性、安全、无障碍                           |
   | Integration       | 上游/下游系统、契约、数据归属                                |
   | Edge Cases        | 空输入、并发访问、部分失败、规模上限                         |
   | Constraints       | 硬约束：截止日期、预算、技术栈、合规                         |
   | Terminology       | 含义因干系人而异的术语（如 "user"、"order"）                 |

2. **苏格拉底式追问（kueiku）**

   🔴 CHECKPOINT · 强制调用 kueiku skill 进行苏格拉底式分析，挖掘用户描述中未显式表达的隐藏问题。跳过此步 = clarify 失败。

   - 用 kueiku 的问题诊断方法论（苏格拉底追问、5 Whys、根本原因分析）对用户描述做深度审视
   - 目标：暴露隐藏假设、未声明的约束、边界条件失效、失败模式、安全隐患
   - 产出：隐藏问题清单 + 每个问题的推荐解决方案
   - 这些隐藏问题必须写入后续 `proposal.md` 的 `## Clarifications` 节，并在 `apply` 阶段解决
   - 若隐藏问题影响范围或可行性，升级为下一步的正式提问项

3. **选至多 5 个高影响问题**

   - 按影响排序有歧义/缺失的分类（猜错会阻塞实施 → 高；猜错是装饰性 → 低）。
   - **上限 5 个问题**。若仍有更多分类，回落到合理默认（见步骤 5）并在提案中注明。
   - **多选优先**：每个问题优先设计为选择题（2-4 个具体选项 + "其他"逃生口），而非开放式问答。选择题降低用户回答成本，也让选项本身暴露设计空间。
   - **方案对比**：当问题涉及设计决策点时（非简单事实确认），不要只问"你要 A 还是 B？"——提出 2-3 个方案并附权衡对比表，给出你的推荐。用户可以否决而非从零思考。

   > **示例——简单事实确认：**
   > Q: "限流窗口用固定窗口还是滑动窗口？"
   > A: 选择题 → 固定窗口 / 滑动窗口 / 令牌桶
   >
   > **示例——设计决策点：**
   > Q: "Redis 不可用时的降级策略？"
   > 方案对比：
   > | 方案 | 复杂度 | 一致性 | 可用性 |
   > |------|--------|--------|--------|
   > | A. 本地内存 LRU | 低 | 低（多实例不一致） | 高 |
   > | B. 本地计数+定期同步 | 中 | 中 | 高 |
   > | C. 拒绝请求+503 | 低 | 高 | 低 |
   > **推荐：** 方案 A — 当前规模下单实例足够，复杂度最低。

4. **通过 AskUserQuestion 工具一次批量提问**

   🔴 CHECKPOINT · 🛑 STOP：批量提问前确认每个问题都满足"猜错会阻塞实施"标准；装饰性歧义用默认值即可，不要塞满 5 个名额。

   把 ≤5 个问题放在单个 AskUserQuestion 调用里，让用户一次答完。不要逐个审问。

5. **对未问的分类静默应用合理默认**

   默认值不在提案中标记为假设 —— 它们是行业基线。仅当用户显式覆盖时才偏离。

   | 分类                  | 默认                                                     |
   | --------------------- | -------------------------------------------------------- |
   | NFR.Data retention    | 领域行业标准（如 90 天审计日志）                         |
   | NFR.Performance       | Web：p95 < 200ms / 移动：p95 < 500ms                     |
   | NFR.Availability      | 单区域、工作时间 SLO                                     |
   | NFR.Accessibility     | WCAG 2.1 AA                                              |
   | NFR.Logging           | 结构化日志，无 PII                                       |
   | NFR.Error reporting   | Sentry 级：错误 + 栈，无用户数据                         |

6. **每个答案到达时写入 proposal.md**

   用户回答后，追加到 `specmark/changes/<name>/proposal.md`：

   ```markdown
   ## Clarifications

   - **[Functional Scope]** Q: <问题文本>
     A: <用户回答，原样或轻度改写>
   - **[NFR]** Q: <问题文本>
     A: <用户回答>
   ```

   增量写入 —— 每个已答问题一条 —— 不是最后批量。如果 `proposal.md` 尚不存在，仅用 `## Clarifications` 节创建它；`propose` 会填充其余。

7. **交给 propose**

   所有答案记录后，提示："澄清已捕获。运行 `/specmark propose <name>` 生成完整提案。"

**提问设计规则**

以下判据在把问题交给用户前逐条过。它们不改动 8 分类扫描与 ≤5 问上限，只决定每个选择题的形状、收尾与措辞。

1. **路由问题与品类菜单 —— 先过「选一行决定了多少」判据**

   选择题和表格的每一行都在替用户做一部分决定。把每一行按下表分类，落在品类菜单一列的坚决删除，换成导航词或动作词。

   | 判据               | 合法：路由问题                                               | 禁止：品类菜单                                                   |
   | ------------------ | ------------------------------------------------------------ | ---------------------------------------------------------------- |
   | 选一行决定了多少   | 几乎不决定 —— 圈出对话邻域，产品形态仍然敞开                  | 直接决定产品形态 —— 替用户挑好了成品                              |
   | 正例               | 领域词（工作、学习、健康、财务、数据监测）、动作词（录入、审批、看板、处理异常） | 品类词（CRM、ERP、电商、医疗、教育、工厂）、细分功能名（增肌、睡眠、记账、经期） |
   | 反例（同一问题的两种问法） | 「这套东西主要给谁用、谁每天碰？」——答案圈定干系人，不圈定产品 | 「你是要做 CRM 还是 ERP 还是电商后台？」——选了 CRM 就等于认领一个中位数产品 |
   | 选完之后你还能思考吗 | 能 —— 从这一行继续往下建                                      | 不能 —— 你已经停止思考                                            |
   | 用户实际付出       | 一个词                                                       | 他真正想要的东西                                                  |

   品类菜单还会返回第一行：多数用户不细读就点第一项，于是提问者把第一行悄悄预设成了答案，范围在还没开始实施之前就已经塌掉。**8 分类扫描的结果（Functional Scope / Domain / UX / NFR / Integration / Edge Cases / Constraints / Terminology）是内部分类框架，不得直接作为品类菜单呈现给用户。** 它是你组织问题的坐标，不是选项列表；从扫描派生问题时，把分类名转写成用户世界里的导航词与动作词。

2. **每批提问以互斥 fork 收尾**

   批量提问的最后一条必须是「不对的话大概是这两个之一」式收尾，让用户否决你的整体理解，而不是逐条答完题之后范围仍然悬空。

   模板句式（可复制）：

   ```
   按上述理解，我会把范围定成：<一句话概述你的整体理解>。
   不对的话，大概是这两个之一：
     ① <最可能的反对意见 —— 选它你会改写定义>
     ② <第二可能的反对意见 —— 选它你也会改写定义>
   ```

   fork 检验判据 —— 任一条不过就重写这两个 fork：

   - **后果相异**：选 ① 与选 ② 会让你写出不同的 `proposal.md`。若两者殊途同归，它们是伪装成选项的措辞，合并成一条。
   - **真的互斥**：同一个定义不能同时对 ① 和 ② 点头。若可以，说明漏掉了第三种真实可能，补进来再判。
   - **不是开放收尾**：禁止「有什么想法都可以说」「还有其他意见吗」式收尾 —— 它返回空值，把组卷成本还给用户。开放逃生口放在各选项的「其他」上，不放在收尾句上。

3. **零元语言呈现，配删除测试**

   向用户呈现提问时不暴露内部坐标。以下内容对用户零元：

   - 分类名、阶段名、子命令名（「这是 NFR 维度的问题」「现在处于 apply 阶段」「按步骤 3 的口径」）
   - 提问预算本身（「这是 5 个问题里的第 3 个」）—— 预算纪律是约束你提问密度的，不是交给用户的进度条
   - skill 内部机制词（自动链、复杂度短路、收敛轮数、脚本名）

   规则与测试成对使用。写完每句要呈现给用户的文字后做一次**删除测试**：删掉这句，提案会变差吗？没有变差 → 这句是写给你自己的，删掉。凡是需要向用户解释「我为什么这么问」的句子，十有八九过不了删除测试；把解释换成行动本身。

   **绝不把磁盘文件、上一轮对话或自我推断当成本轮答案。** 问了问题就停下来等回答 —— 不得去读一份磁盘上的旧文件、翻一段历史对话、或用「用户大概是想 X」填充答案继续往下走。本轮答案只来自本轮用户。

> 来源：mouse-lin/finesse-brief 仓 SKILL.md:137（路由 vs 品类菜单判据）、:161/:176/:194/:211（fork 收尾句式与真假 fork 例）、§0.G :356-360 与 §0.H :362-380（零元语言、删除测试）、:353（一条消息然后停下；磁盘文件/自我推断不当本轮答案）——2026-10 对标吸收，克隆为本地只读参考，不随 skill 分发。

**提问预算纪律**

≤5 问是硬上限（见 Guardrails），管的是「最多问几个」。以下三条纪律在预算之内进一步压缩提问量，与上限互补不冲突：上限截断超额提问，纪律消减本该避免的提问。

1. **已知信息绝不重问。** 用户描述里已经说过的、代码与文档里已经承载的、步骤 0 调研已经确认的，一律不再进问题列表。步骤 0 的调研产出就是这条纪律的执行处 —— 「你的代码在哪」式低价值问题即属违例：答案明摆着，问了只是浪费用户一轮。
2. **能合并则合并进同一消息。** 同属一个分类、同一个决策点的歧义合并成一题，不把一个决策切成三问。例如「截止日期是哪天？」与「是硬截止还是软截止？」是同一决策点（时间约束）的两面，合成一题：「时间约束是硬截止（哪一天）还是软截止（尽量）？」
3. **超预算一律转默认值。** 超过 5 问上限的歧义不再新增提问，按步骤 5 的默认表静默应用合理默认，并在提案中注明该默认值。超预算不是提第 6 个问题的理由。

> 来源：mouse-lin/finesse-brief 仓 SKILL.md:39（already-known is never re-asked）、:31（预算之外再追问属设计缺陷）——2026-10 对标吸收，克隆为本地只读参考，不随 skill 分发。

**输出**

```
## 澄清完成

**变更：** <name>
**已问问题：** N
**应用默认值的分类：** <列出用了默认的分类>

已捕获到 `proposal.md` → `## Clarifications`。
下一步：`/specmark propose <name>`
```

**Guardrails**

- **至多 5 个问题** —— 硬上限。如果发现第 6 个，它必须是默认值。
- **不问论述题** —— 仅简答或选择。
- **默认值是静默的** —— 不要把它们作为"需确认的假设"浮现；那会破坏目的。
- **对现有产物只读**，除了追加到 `proposal.md` 的 `## Clarifications` 节。不碰 design.md 或 tasks.md。
- **请求具体时整个跳过** —— clarify 是可选的，非强制。如果 0 个分类有歧义/缺失，宣布"无需澄清"并直接建议 `/specmark propose`。
- **绝不阻塞 propose** —— 如果用户拒绝回答，用默认值继续 propose；不停滞。

**Fluid Workflow Integration**

- 可在 `propose` 前任何时候调用，包括 `explore` 之后。
- 如果 `propose` 已在进行中且中途遇歧义，可委托回 `clarify` 问一个针对性问题，然后恢复。
- Clarify 不消耗 `explore` 的角色：explore 是开放式思考；clarify 是 8 类有界问答。
